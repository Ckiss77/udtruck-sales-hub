4 นาที
คิว: เปิดด้วยคำถามชวนคิด แล้วชี้ภาพ daily snapshot ด้านขวา หลีกเลี่ยงการอ่านตัวเลขตัวอย่างให้ฟังเหมือนเป็นผลวิเคราะห์จริง
บทพูด

สวัสดีทุกท่าน ขอบคุณที่ให้โอกาสเรานำเสนอ Project B วันนี้เราจะพูดถึงวิธีเปลี่ยนข้อมูลสินค้าบน marketplace และ delivery app ให้เป็นภาพราคาที่ทีมเทียบกันได้ในมุมเดียว ตั้งแต่ราคาสินค้า ส่วนลด ไปจนถึง voucher ที่มีผลต่อราคาที่ผู้ซื้อเห็น

โจทย์ใน brief ระบุให้ดึงข้อมูลสินค้าและราคาเป็นรายวันจาก Shopee, Lazada, TikTok Shop และ 7-Eleven Delivery ครอบคลุมสินค้า Nestlé และคู่แข่งในสี่หมวด สิ่งที่เราต้องตอบให้ได้ไม่ใช่แค่ว่า “ราคาหน้าร้านเท่าไร” แต่ต้องเห็นด้วยว่าราคานั้นประกอบจากอะไร เป็นสินค้าหรือ pack แบบไหน และเงื่อนไขโปรโมชันใช้ได้เมื่อใด

แนวคิดของเราคือสร้าง daily SKU view ที่เชื่อมสามอย่างเข้าด้วยกัน คือข้อมูลสินค้าที่ตรงกัน, price ladder ที่แยกส่วนลดแต่ละชั้น, และหลักฐานพร้อมเวลาที่เก็บ เมื่อข้อมูลมีข้อจำกัดหรือ capture ไม่สำเร็จ ระบบต้องแสดงสถานะให้ทีมรู้ แทนการปล่อยตัวเลขที่ดูครบแต่ตรวจย้อนกลับไม่ได้

ภาพตัวอย่างที่เห็นเป็นเพียงแนวทางหน้าจอ ไม่ใช่ข้อมูลตลาดจริง และยังไม่เชื่อมต่อแพลตฟอร์ม วันนี้เราจะเริ่มจากขอบเขตข้อมูล อธิบายวิธีตรวจสอบและส่งมอบ จากนั้นสาธิต flow ให้เห็นการใช้งานจริงของ portal

ประโยคหลัก: “หนึ่ง SKU, หนึ่งมุมมองที่เทียบราคาและเงื่อนไขได้ พร้อมรู้ว่าข้อมูลมาจากไหนและเก็บเมื่อไร”

ขอบเขตข้อมูล · ตั้งแต่ SKU ถึงช่องทาง

5 นาที
คิว: ไล่จากซ้ายไปขวา: ช่องทาง → Nestlé brands → competitor categories → price ladder. หยุดชี้รายการที่จะต้องให้ Nestlé ยืนยัน
บทพูด

ขอบเขตใน brief มีสี่ช่องทาง คือ Shopee, Lazada, TikTok Shop และ 7-Eleven Delivery. ฝั่ง Nestlé มีเจ็ดกลุ่ม ได้แก่ S-26, Nestlé Milk, Food and Beverages, Purina, Dolce Gusto, Health Science และ Professional. ฝั่งคู่แข่งครอบคลุม Infant Nutrition, Coffee, Pet Food และ Adult Nutrition

เราจะเริ่มการจับคู่ที่ระดับ SKU และ variation เพราะชื่อสินค้าอย่างเดียวไม่พอที่จะเทียบราคาให้ยุติธรรม ขนาดบรรจุ จำนวนชิ้นต่อแพ็ก หรือรูปแบบแพ็กอาจต่างกัน เราจึงเสนอให้เก็บข้อมูลอ้างอิงที่จำเป็น เช่น product/variant, store, platform, เวลาเก็บ, จำนวนชิ้นหรือหน่วยต่อแพ็ก และหลักฐานของหน้าสินค้า แล้วคำนวณราคาเทียบต่อหน่วยตามกติกาที่ตกลงร่วมกัน

ส่วน price ladder จะแยกอย่างน้อย list price, SKU discount, brand หรือ store voucher, platform voucher และ shipping ออกจากกัน เพื่อไม่ให้ลดซ้ำหรือเปรียบเทียบราคาคนละนิยาม ตัวอย่างใน brief ยังแสดง final price, final price per piece และ remark ด้วย เราจะยืนยัน data dictionary กับทีมใน discovery ก่อนล็อก schema และหน้าจอ

สำหรับ 7-Eleven Delivery ราคาหรือการจัดส่งอาจผูกกับพื้นที่และสาขา ดังนั้นเราต้องตกลง location ที่ใช้เป็นจุดอ้างอิงให้ชัดเจนก่อนเก็บข้อมูล หากไม่กำหนดพื้นที่ ตัวเลขที่เปรียบเทียบกันอาจไม่ใช่เงื่อนไขเดียวกัน

คู่แข่งและ target SKU ต้องมาจากรายการที่ Nestlé อนุมัติ ไม่ควรเดาจาก keyword อย่างเดียว เราจะใช้รายการนั้นเป็น product master ตั้งต้น แล้วส่ง exception ให้เจ้าของข้อมูลยืนยันเมื่อพบชื่อหรือ pack ที่ไม่ตรงกัน

ประโยคหลัก: “เราจะเทียบสินค้าในระดับ pack/variation ที่ตรงกัน และแสดงเงื่อนไขราคา ไม่ทำให้ตัวเลขดูเทียบกันได้ทั้งที่คนละฐาน”

วิธีทำงาน · จากหน้าร้านสู่ราคาที่เทียบกันได้

6 นาที
คิว: เดินตาม 4 ขั้นจากซ้ายไปขวา จากนั้นชี้ price ladder และอธิบายว่า shipping แยกจาก net price
บทพูด

วิธีทำงานแบ่งเป็นสี่ขั้น ขั้นแรกเก็บข้อมูลรายวันจากหน้า product และหน้ารวม voucher ในแต่ละช่องทาง โดยเริ่มจากวิธีที่ได้รับอนุญาตและเหมาะกับแหล่งนั้น เราจะบันทึก timestamp และสถานะ capture ทุกครั้ง เพื่อแยกข้อมูลล่าสุดออกจากข้อมูลที่มีปัญหา

ขั้นที่สองคือจับคู่ SKU กับ product master ของ Nestlé เราจะเทียบแบรนด์ ชื่อสินค้า ขนาด แพ็ก และ variation ถ้าคู่ไม่ชัดเจนจะส่งเข้า exception queue เพื่อให้คนตรวจ แทนการ auto-match อย่างมั่นใจเกินจริง ทั้งนี้ยังต้องกำหนด ID ของ SKU และกติกาการอนุมัติร่วมกัน

ขั้นที่สามคำนวณราคาโดยเก็บ component แยกกัน เริ่มจาก list price หักส่วนลดที่ติดกับ SKU แล้วพิจารณา voucher ร้านค้าหรือแบรนด์และ platform voucher ตามเงื่อนไขที่พบ ผลลัพธ์เป็น net price โดยแยกค่าส่งออก และคำนวณราคาต่อหน่วยจากจำนวนหน่วยในแพ็ก เฉพาะ voucher ที่ใช้ร่วมกันได้เท่านั้นที่จะถูกนำมารวม ไม่รวมคูปองที่เงื่อนไขขัดกัน

ขั้นที่สี่คือการตรวจและส่งมอบ เราจะตรวจ missing fields, ราคาเปลี่ยนผิดปกติ, SKU ที่ match ไม่ได้ และ capture failures. ทีมเห็นทั้งผลที่ผ่านและรายการที่ต้องติดตาม พร้อมเวลาและหลักฐานอ้างอิง การใช้ภาพ capture ต้องตกลง retention, การเข้าถึง และขอบเขตข้อมูลส่วนบุคคลกับ Nestlé ก่อน

แหล่งข้อมูลอาจใช้ API เมื่อมีและได้รับอนุญาต หรือ browser/app automation เมื่อเหมาะสม แต่เราไม่ถือว่าทุกช่องทางจะเข้าถึงได้แบบเดียวกัน Discovery จึงต้องทดสอบแต่ละแหล่งก่อนล็อก coverage. หากช่องทางเปลี่ยนหน้า เราจะมี monitoring, retry และกระบวนการให้คนช่วยตรวจกรณีที่ automation ไปต่อไม่ได้ โดยอยู่ภายใต้เงื่อนไขการใช้งานของแพลตฟอร์ม

ผลลัพธ์ไม่ได้มีแค่หน้าจอ แต่ประกอบด้วย structured output, data dictionary, run status และ issue path เพื่อให้ทีมตรวจต่อหรือส่งต่อให้ระบบภายในได้ตามปลายทางที่ตกลง

ประโยคหลัก: “ราคาแต่ละชั้นคำนวณแยก เก็บหลักฐาน และทำให้ความไม่แน่นอนมองเห็นได้”

แผนส่งมอบ · เริ่มเล็ก ตรวจให้ชัวร์ แล้วขยายอย่างควบคุมได้

6 นาที
คิว: ไล่ timeline ทีละช่วง แล้วชี้ security box. พูดชัดว่า 6 สัปดาห์เป็น estimate หลัง kickoff และต้อง rebaseline เมื่อเห็น access/ปริมาณ SKU
บทพูด

เราเสนอ roadmap เบื้องต้นหกสัปดาห์หลัง kickoff. สัปดาห์แรก align รายการ SKU, คู่แข่ง, ร้านหรือ location, output, owner และเกณฑ์ตรวจรับ สัปดาห์ที่สองถึงสามวาง data model และสร้างช่องทางนำร่องให้ครบ price ladder พร้อมหลักฐาน สัปดาห์ที่สี่ถึงห้าเพิ่มช่องทางที่เหลือ รวม TikTok Shop และ 7-Eleven ตามความพร้อมในการเข้าถึงและผล feasibility. สัปดาห์ที่หกทำ UAT, แก้ exception, ส่งคู่มือและ runbook

ตัวเลขหกสัปดาห์นี้เป็น estimate สำหรับวางแผน ไม่ใช่คำมั่นที่แยกจากจำนวน SKU, ความพร้อมของ product master, access approvals, พื้นที่ delivery และความเปลี่ยนแปลงของแต่ละ platform. เมื่อเรารู้ปัจจัยเหล่านี้ เราจะปรับแผนและบอก dependency ให้เห็นก่อนเริ่ม build

ก่อนขึ้น production เราเสนอ acceptance gates ที่วัดได้ร่วมกัน เช่น coverage ของ SKU และ field, ความถูกต้องของ price ladder, การตีความ voucher eligibility, run success, freshness และการตรวจย้อนหลังจากหลักฐาน เราไม่กำหนด threshold เองฝ่ายเดียว เพราะต้องรู้ว่าแต่ละ metric ใช้ตัดสินใจอะไรและยอมรับข้อยกเว้นแบบใด

Cloud security เป็นส่วนหนึ่งของแผนตั้งแต่ต้น Brief ระบุ identity and access lifecycle, encryption, architecture, service level, support model, hosting environment, BIA และ PIA. สำหรับผู้ให้บริการรายใหม่ยังต้องส่ง RFP cloud questionnaire, แสดง ISO 27001, เข้าร่วม periodic assessment และให้ evidence. เราจะเตรียมเอกสารและระบุ owner ต่อ control แต่สถานะ certification และหลักฐานต้องอ้างอิงสถานะจริงของบริษัท ไม่ควรกล่าวว่าผ่านแล้วหากยังไม่ได้ตรวจ

production architecture และที่ตั้งข้อมูลต้องผ่านการทบทวนกับ Nestlé Security/IT ก่อนเลือกบริการ cloud หรือเปิดใช้จริง สำหรับ mockup วันนี้เราใช้หน้า static เพื่อสื่อ flow เท่านั้น จึงไม่ใช่แบบสถาปัตยกรรม production

ประโยคหลัก: “เราผูก timeline กับ access, SKU scope และ acceptance gates แล้วให้ Security ตรวจ architecture ก่อน production”

ข้อเสนอเริ่มต้น · ข้อมูลที่ทีมตัดสินใจต่อได้ทันที

4 นาที
คิว: สรุป 4 deliverables. ก่อนพูดเรื่องราคา ให้เปิด commercial sheet ที่กรอกตัวเลขจริงแล้วเท่านั้น; อย่าอ่าน [กรอกตัวเลขจริง] ต่อหน้าลูกค้า
บทพูด

เมื่อจบโครงการ ทีมจะได้รับ daily SKU view ที่แสดงราคาและสถานะข้อมูล, การเปรียบเทียบที่แยก store/platform voucher, evidence ที่ย้อนตรวจได้ และ operational handover ซึ่งประกอบด้วย data dictionary, runbook, issue path และเกณฑ์ตรวจรับ

เรื่อง commercial เราจะแยกค่าใช้จ่ายครั้งเดียวสำหรับ discovery, data model, source connectors, QA/UAT และ handover ออกจากค่าใช้จ่ายรายเดือนสำหรับการ run, monitoring, support และ hosting. หากมีค่าใช้จ่ายต่อ platform หรือเพิ่มขอบเขต เราจะแสดงเป็น line item หรือ rate ที่มีสมมติฐานชัด ไม่ซ่อนอยู่ในตัวเลขรวม

เพื่อให้ตัวเลขมีความหมาย เราต้องผูกกับจำนวน SKU, จำนวน source, ความถี่ของรอบเก็บ, พื้นที่ 7-Eleven, ระดับ support และข้อกำหนด hosting. ใน proposal ฉบับส่งจริงเราจะใส่ราคา setup, monthly run, hosting และ option เพิ่มเติมเป็นบาท พร้อม activity breakdown. ราคาที่ระบุวันนี้ต้องได้รับการอนุมัติจากทีม commercial ของเราก่อนนำเสนอ และเราไม่เสนอ fixed fee โดยไม่บอก assumptions หรือ change control
